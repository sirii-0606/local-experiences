# 2026-09-26-10 · M9.1: live weather context

## What changed
- `main` was fast-forwarded to M8 (`80765aa`) at the team's request. All core milestones are on `main`.
- **`backend/app/weather.py`** (new) uses stdlib `urllib` against Open-Meteo, which needs no key.
  - It queries the **fixed Jaipur centre**, never the traveler's position, and fetches hourly temperature, precipitation, probability and WMO code in IST.
  - `classify()`: rain means WMO 51–67/80–82/95–99, ≥0.5 mm or ≥70%; heat means ≥38 °C; everything else is clear.
  - `forecast(day)` caches for 30 min and returns **None on any failure**, so the product behaves exactly as before when offline.
  - `plan_risks()` finds upcoming outdoor, weather-sensitive stops whose hours overlap forecast rain or heat.
- **API:**
  - `GET /weather?at=` returns live conditions for that hour.
  - `POST /context/check` returns `{available, risks, proposed}`. It **proposes** a weather `ContextEvent` and never applies it (doc §9.2: detect → decide it's material → explain → the user confirms). There's no proposal if the state already has that weather.
- **Frontend:**
  - A live weather chip beside the demo clock, e.g. "☀ 33°C · 7% rain · live", or "live weather offline".
  - A "Check live forecast" button in the disruption panel. It shows ✓ no risk, or ⚠ one line per risky stop plus a **"Replan for rain/heat"** button, which runs the normal `/events` flow and diff.
- **Tests:** `tests/test_weather.py` has 12 tests (78 pass in total, 1 skipped). They cover classification, caching, outage → None, rain over an outdoor stop → risk + proposal, rain over indoor or past stops → nothing, no proposal when the state already knows, offline behaviour, `/weather`, and heat. All use a canned forecast, so there's no network in tests.
- **Docs:** `docs/api.md` (2 endpoints), `decisions.md` (the weather row), and the roadmap (M9 🟡 with item order).

## Why
Doc §4 (context layer) and §9 (adaptation): the system should *detect* disruptions, not just react to buttons. This keeps both earlier choices: demos stay reproducible (live data never silently changes results), and the traveler stays in control.

## Known gaps
- `ponytail:` weather in the engine is window-wide, not per hour. Accepting "rain" treats every outdoor stop ahead as rained out, even if the rain is only at 17:00.
- There's no automatic polling. The traveler presses "Check live forecast". Add a timer, or check after each `/events` call, if wanted.
- The demo clock can point at dates Open-Meteo doesn't cover (roughly more than 16 days ahead, or the far past). That shows as "offline", which is harmless.
- Traffic is still distance-based only.
