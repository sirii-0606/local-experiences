# 2026-09-26-05 · M4: dynamic adaptation (replanning)

## What changed
- `main` was fast-forwarded to M3 (`3651a15`) at the team's request, with no PRs.
- **`backend/app/engine/adapt.py`** (new) provides `replan(itinerary, state, event, seed) -> Replan(itinerary, state, changes)`. It follows doc §9.2:
  1. **Freeze the past.** Stops that have ended become `completed`; the one in progress becomes `active`.
  2. **New state.** The traveler is now free at max(now, end of the current stop) + delay. The event updates the state: rain/heat → `weather`, fatigue → relaxed pace, budget change → new budget.
  3. **Walk the upcoming stops in order under the new state.** Broken unlocked stops are marked `replaced`. Broken locked stops are reported as `at_risk` and **never moved**. The exception is when the provider cancels or closes the stop, which overrides the lock.
  4. **Repair each broken stop inside the gap it left.** In order: retime the same experience, then an alternative that shares at least one tag with the original (preserving intent), then drop it.
  5. **`Change`** records `action` (`retimed`/`replaced`/`dropped`/`at_risk`), `reason` (why the original broke), `new_stop`, and `why` (the engine's reasons for the new pick).
- **Context in the engine:**
  - `TravelerState.weather` (`clear`/`rain`/`heat`) is new.
  - `feasibility.rained_out()` is a hard constraint in `check`, and `validate` now flags rained-out stops.
  - Heat is a soft penalty in ranking.
  - `rank.is_strenuous()` is extracted and shared.
- **Itinerary helpers:**
  - `upcoming()` returns only proposed/confirmed stops. `gaps` and `validate` now plan from the state's position and time, after anything completed or in progress.
  - `fill_gap(..., skip=)` is new. "Already used" now means active stops only, so a replaced stop's experience can be retimed.
- **Reason wording:** mid-day fills now say "in time for your next stop at HH:MM" instead of "cutoff".
- **`backend/tests/test_adapt.py`** has 9 tests on one realistic day: kite-making, a locked lunch, Jantar Mantar, a locked City Palace booking, and the puppet show.
  - One test per event type, plus a check that locked stops at risk are reported rather than moved, and that an irrelevant event changes nothing.
  - Every result must pass `validate` and the independent sequence check, and locked stops must stay identical.
- **`decisions.md`:** adds the replanning event rules and the three-tier "good alternative" rule (retime, replace, drop). The +20% price rule was removed, because the remaining budget already bounds it.

## Why
Doc §9: adaptation is core behaviour. "Do not regenerate the entire trip when only one node fails."

- **Lunch overruns 40 min:** Jantar Mantar is dropped, because nothing comparable fits 14:10–15:00. The City Palace booking and the puppet show are untouched.

## Known gaps
- Fatigue sets a relaxed pace but doesn't remember it across later events. The API should keep the returned `Replan.state` as the new state.
- A "traveler discovers something unexpected, re-optimise around it" trigger (doc §9) isn't modelled yet. It's just `plan()` after the user locks the new stop.
- There's no learning from accept/reject of alternatives yet (M8).
- The repair uses the first gap after the original's start. If a delay pushes past several stops, each broken stop competes for the same first gap in order. That's fine for a demo.
